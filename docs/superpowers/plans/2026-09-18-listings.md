# Listings Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Admins (Super Admin / Area Admin) can create a Listing against a Unit (or one of its Spaces), browse all Listings, view/update a Listing's status, and see a Unit's Listings from the Unit detail page — wired to real Supabase data, replacing the static mock screens a parallel design pass built at `/listings`, `/listings/new`, `/listings/[listingId]`.

**Architecture:** Same pattern as every prior plan — Server Components read via RLS-gated Supabase queries, Server Actions handle writes with a UX-level role check backstopped by already-deployed RLS. No new migrations: `listings` and `listing_status_history` already exist from `0001_phase1_schema.sql`, including a `BEFORE UPDATE` trigger that auto-appends to `listing_status_history` on any status change — nothing in this plan needs to write that history table directly.

**Tech Stack:** Next.js Server Components/Actions, Supabase (`@supabase/ssr`), Tailwind, the shared `Badge` component (`@/components/badge`) and `BadgeTone` type (`@/lib/ui/badge-tone`) a parallel session already introduced and this plan's real pages should keep using for visual consistency.

## Important Context: a Parallel UI Design Pass Already Landed

A separate session built a full admin UI shell (Dashboard/Units/Owners/Owner search/Listings/Contact requests/Verification/Users & areas) on top of this project's real Units/Owners functionality, restyling the real pages (tabs, `Badge`, a sidebar `AppShell`) and adding **mock-data-only** screens for the parts not built yet (Listings, Contact requests, Verification, Owner search — each backed by a `src/lib/mock/*.ts` file with an in-memory array, explicitly for design reference).

This plan's job is to wire the **Listings** mock screens to real data, in place — not to build new pages from scratch. `src/lib/mock/listings.ts` and its test stay untouched (they're a design-reference artifact for whoever wires the other three mock screens later); this plan's real pages stop importing from it and import from a new `src/lib/listings/status-labels.ts` instead.

## Schema This Plan Assumes (already deployed — do not re-create)

- `listings(id uuid, unit_id uuid not null, space_id uuid nullable, listing_type text not null check in ('rent','sale','rent_sale'), asking_rental numeric, selling_price numeric, rented_price numeric, availability text, listing_status text not null default 'draft' check in ('draft','pending_verification','available','reserved','rented','sold','owner_occupied','not_for_rent','inactive','archived'), exclusive boolean, exclusive_date date, exclusive_by uuid, banner_status text, available_from date, last_verified_date date, created_by uuid, created_at, updated_by uuid, updated_at, remarks text)`.
- RLS: `listings_select_all` — any authenticated user can SELECT (no owner PII on this table). `listings_insert_admin` / `listings_update_admin` — restricted to `super_admin` or the `area_admin` assigned to the unit's area, via the same `area_id_for_unit()` helper every prior plan's RLS has used.
- `listing_status_history` — `BEFORE UPDATE` trigger `trg_listing_status_history` on `listings` auto-inserts a row whenever `listing_status` changes. This plan's status-update action does a plain `UPDATE`; the history logging is automatic and not this plan's concern.

## Global Constraints

- Listings carry no owner PII directly (spec's separation principle, §11) — any authenticated user (including `sp`) may read the `listings` table and the Unit-detail "Listings" tab; only *creating/editing* a listing is admin-gated. This matches RLS exactly — do not add a role gate around reading listings that RLS doesn't itself enforce.
- Never overwrite listing history — every status change goes through the existing trigger; do not hand-write inserts into `listing_status_history` anywhere in this plan.
- A listing's Unit/Space are reused, never re-keyed (spec §40) — the create-listing form must be reached with a `unitId` already known (from the Unit detail page), never ask the admin to retype unit info.
- `listing_status` values are exactly the 10 DB CHECK literals; `listing_type` is exactly `rent | sale | rent_sale` — use these literal strings, matching `src/lib/owners/status-labels.ts`'s established pattern for enum/label modules.
- Light theme, white background, sky-blue accents, `Badge`-based status pills — match the already-restyled `src/app/(app)/units/[unitId]/page.tsx` and `src/app/(app)/admin/users/page.tsx` conventions exactly (both already use `Badge`, `FIELD_CLASSES`, and rounded-2xl cards).

```typescript
"use server";

import { redirect } from "next/navigation";
import { getCurrentProfile } from "@/lib/auth/get-current-profile";
import { createClient } from "@/lib/supabase/server";
import type { ListingStatus } from "@/lib/listings/status-labels";

export async function createListing(formData: FormData) {
  const actor = await getCurrentProfile();
  if (!actor || (actor.role !== "super_admin" && actor.role !== "area_admin")) {
    redirect("/");
  }

  const unitId = String(formData.get("unitId"));
  const spaceId = String(formData.get("spaceId") ?? "");
  const listingType = String(formData.get("listingType"));
  const askingRentalRaw = String(formData.get("askingRental") ?? "");
  const sellingPriceRaw = String(formData.get("sellingPrice") ?? "");
  const availableFrom = String(formData.get("availableFrom") ?? "");
  const remarks = String(formData.get("remarks") ?? "");
  const intent = String(formData.get("intent"));
  const listingStatus: ListingStatus =
    intent === "pending_verification" ? "pending_verification" : "draft";

  const supabase = await createClient();
  const { error } = await supabase.from("listings").insert({
    unit_id: unitId,
    space_id: spaceId || null,
    listing_type: listingType,
    asking_rental: askingRentalRaw ? Number(askingRentalRaw) : null,
    selling_price: sellingPriceRaw ? Number(sellingPriceRaw) : null,
    available_from: availableFrom || null,
    remarks: remarks || null,
    listing_status: listingStatus,
    created_by: actor.id,
    updated_by: actor.id,
  });

  if (error) {
    redirect(`/listings/new?unitId=${unitId}&error=create_failed`);
  }

  redirect(`/units/${unitId}?listing_created=1`);
}
```
